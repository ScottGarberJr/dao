# DAO V1 plan

## Objective

Establish the initial Codex-centered DAO architecture described in [DAO architecture](../docs/dao-architecture.md): durable project knowledge in GitHub, reusable declarative teams, MCP-accessible external capabilities, and automation subordinate to Codex.

## Dependencies

- Team definitions are jointly agreed before a team is used.
- Tool and actor definitions are agreed before an MCP or n8n implementation is created.
- Outlook email/calendar capabilities require the relevant access and permissions.
- Figma and GitHub capabilities require their respective MCP connections and permissions.
- Credentials, mailbox contents, and other sensitive data remain outside Git.

## Feature 1 — Codex and durable project knowledge

Define Codex as the DAO's primary driver and make the DAO's current knowledge discoverable across desktop, mobile, and VS Code work.

### Acceptance criteria

- [x] `project/docs/`, `project/plans/`, and `project/sessions/` follow the universal repository convention.
- [x] `project/docs/dao-architecture.md` defines the initial DAO architecture.
- [x] Root `AGENTS.md` defines DAO-specific discovery and the normal-project exception.
- [x] The distinction between Codex, models, teams, skills, tools, actors, MCPs, and automation is documented.

## Feature 2 — Initial reusable team definitions

Create the initial reusable teams in `teams/<team>/`. Each team has a `README.md` for its shared purpose and workflow. Major lifecycle stages use uppercase documents; lowercase documents support specific tasks. Team documents define purpose, responsibilities, preferred approaches, technical preferences, tools, standards, constraints, expected outputs, escalation rules, scope, permissions, reporting, and any cadence requirements.

### Work items

- [ ] Review and accept `teams/dev/README.md` for DevTeam.
- [ ] Jointly define the DevTeam lifecycle-stage documents, beginning with `teams/dev/DESIGN.md`.
- [ ] Review the standard project `project/docs/design.md` template and the conditions for expanding it into `project/docs/design/`.
- [ ] Jointly define `teams/ops/README.md` for OpsTeam.
- [ ] Jointly define `teams/research/README.md` for Research.
- [ ] Jointly define `teams/assistant/README.md` for Assistant.
- [ ] Define how Codex resolves the natural references Dev/DevTeam, Ops/OpsTeam, Research, and Assistant.
- [ ] Prioritize the DevTeam workflow documents, then the required Assistant and Ops documents; remaining subdocuments may be completed after V1.

### Acceptance criteria

- [ ] Each initial team has an agreed `README.md` as its Markdown source of truth.
- [ ] Each team definition states scope, permissions, escalation, and expected outputs.
- [ ] No team behavior is permanently embedded in a model-specific prompt or implementation.

## Feature 3 — Initial external tools and MCP capabilities

Define useful, safe external capabilities before implementing them. n8n is an optional MCP-backed implementation platform for Outlook tools and actors; it is not the DAO orchestrator. Direct MCP access is preferred where it is the appropriate interface.

### Work items

- [ ] Define the Outlook email tool use cases and interfaces, covering the two initial inboxes.
- [ ] Define the Outlook calendar tool use cases and interfaces.
- [ ] Define the VPS-hosted n8n MCP boundary, authentication method, and narrow Outlook/OneNote tool surface before connecting Codex.
- [ ] Start the Outlook connection with delegated, least-privilege, read-only tools; define separate approval gates for every write-capable operation.
- [ ] Define the initial actor pattern for repeatable multi-step processes.
- [ ] Define the Figma MCP capability and its intended uses in the DevTeam `DESIGN.md` stage.
- [ ] Define the GitHub MCP capability and its intended uses.
- [ ] Document permissions, safety considerations, limitations, and implementation location for each approved tool or actor.

### Acceptance criteria

- [ ] Each approved tool or actor has a Markdown definition in `tools/`.
- [ ] Tools expose useful operations rather than raw provider endpoints.
- [ ] Actors encapsulate repeatable multi-step workflows without making n8n the DAO orchestrator.
- [ ] No credential or sensitive service data is committed.

## Feature 4 — Interfaces and automation approach

Establish the practical workflow across the ChatGPT desktop/mobile applications and VS Code, and define how future DAO-level automation and schedules are added.

### Work items

- [ ] Document the agreed desktop, mobile, and VS Code workflow when it is defined.
- [ ] Define the schedule format to use when a DAO-level recurring need exists.
- [ ] Add a schedule only when an agreed tool or actor and a defined team requirement justify it.

### Acceptance criteria

- [ ] Project knowledge is usable across the agreed interfaces.
- [ ] Any future schedule names its tool or actor, timing, expected output, destination, and conditions that prevent execution.
- [ ] Automation remains subordinate to Codex's reasoning, planning, coordination, and decision-making.

## Completion

- [ ] All V1 feature acceptance criteria are complete.
- [ ] Any open decisions or pivots are reflected in current documentation and the relevant monthly session record.
