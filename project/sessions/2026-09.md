## 2026-09-02 — DAO architecture scaffold

### Discussion

- Established the DAO repository scaffold from the DAO architecture.
- Confirmed that every repository, including this one, uses `project/` for project-specific docs, plans, and session history.
- Confirmed that team markdowns will be jointly defined and are the future source of truth for team scope, permissions, reporting, and cadence requirements.
- Confirmed that no schedules, recurring automation, teams, external tool definitions, or live Outlook/n8n workflow are defined or enabled yet.

### Decisions

- The DAO repository follows the universal `project/` convention.
- Codex is the DAO's primary driver; n8n is an external tool and actor platform, not the DAO orchestrator.
- DAO-wide reusable team definitions live in `teams/`; project-specific knowledge lives in `project/`.
- Future n8n access is defined through DAO tools or actors and MCP, not an `automation/n8n/` implementation folder.
- Research is an initial team to be jointly defined alongside DevTeam, OpsTeam, and Assistant.
- `tools/` is the DAO registry for future tools, actors, MCPs, APIs, and upstream references. It does not contain cloned source, credentials, or enabled integrations.
- Codex-native skills remain separate from DAO documentation. The repository-level `skills/` placeholder is removed until an actual native skill is warranted.
- ChatGPT Sites is reserved for deploying site demos, not for design work.
- DevTeam's entry document is drafted for review. It uses version plans as its work queue, keeps the user at the acceptance and commit gate, and does not make autonomous team-to-team handoffs.
- Design is a DevTeam lifecycle stage, not a standalone team. Dev's `DESIGN.md`, `PLAN.md`, `BUILD.md`, `TEST.md`, and `DEPLOY.md` documents are its major stages; lowercase documents support specific tasks.
- Teams use folders with a `README.md` entry document. Dev, Research, Assistant, and Ops structures are scaffolded; documents not yet defined are marked pending set up.
- DevTeam's major lifecycle-stage documents and the V1-relevant Assistant and Ops documents use a shared draft section structure. Unknown operating details are represented by visible blank sections for joint definition.
- Candidate tools, repositories, MCPs, and skills are recorded in their relevant workflow documents for review only; none is enabled or approved by the drafts.
- DevTeam's agreed draft flow is discovery, Figma-hosted references and sketch, Figma-driven design, design review, plan, feature-branch build, test, and client review. The project repository retains the project-specific discovery and documentation context.
- Outlook email and calendar access through narrowly scoped n8n MCP tools on the user's VPS is a major V1 requirement. The two Outlook mailboxes, calendar, and a possible OneNote connection must use delegated least-privilege access and begin read-only.
- Instatic has an MCP connector surface for external agents; Coolify documents a built-in MCP endpoint. Both remain candidates pending a security and capability review.
- External capabilities named in DAO Markdown must link to their official documentation or upstream source in the owning document.
- DevTeam owns `discovery.md` as a task document, which a dedicated Dev discovery agent may perform. Research remains a separate future team and is used only when its specialized capability is needed; design receives the resulting Figma reference pages.
- Design must deliver the approved Figma design page plus linked, fleshed-out design documentation to planning. Dev work occurs on feature branches; `main` is the active Coolify deployment branch. Standing staging is deferred, with client-specific Coolify staging or ChatGPT Sites demos/UAT considered later when warranted.
- The DevTeam default commit gate is user-reviewed acceptance criteria, applicable automated checks, Figma visual review for UI work, and a concise change summary with test evidence. The user can explicitly skip a gate or batch features.
- Every project uses `project/docs/design.md` as its default design-document entry point. When a client requests it or the design needs it, sections may be expanded into `project/docs/design/`, while the root document remains the summary and link index.
- The project design-document template covers the product idea and objectives; versioned features; UI and UX; technical details and data model; strategy, content, SEO, marketing, monetization, and policy; references; and open questions, with site- and app-specific guidance where relevant.
- Design work is discussion-first by default. Figma changes or other direct design work require explicit task-level authorization unless the user has told the agent it may work freely.
- The default project deliverables are `project/docs/requirements.md`, `project/docs/design.md`, and `project/docs/architecture.md`. Requirements carries the functional overview and versioned feature scope; design carries UI/UX, Figma, design-system, and branding direction; architecture carries the technical stack, diagrams, site/screen map, data model, APIs, and security roles. A single explicitly labeled combined document is an allowed exception.
- Before planning, DevTeam uses `team-review.md` for the user, Dev agent, and optionally a separately selected independent reviewer to reconcile the three first drafts and approved tool/skill findings. External Copilot or Gemini input must be supplied by the user until a safe, approved connection is defined.
- Planning requires the user's go-ahead after that review. Version and patch documents use numbered feature or fix sections with a name, one-line summary, task checklist, and acceptance-criteria checklist. Version 1 starts with a project-scaffolding/boilerplate feature appropriate to the project; building needs a separate user go-ahead.
- Version plans use `v<major>.0.md`; patches use `v<major>.<patch>.md`. Work sections use `major.patch.item` identifiers, such as `1.0.1` for Version 1.0 and `1.1.1` for Patch 1.1. The DAO plan is renamed `v1.0.md` and follows this hierarchy.

## September 22 — Studio delegation direction

### Discussion

- Reviewed FirstMate's approach and the current Pi, Herdr, Codex, local-model, DAO, and Discord boundaries as reference material rather than adopting its nautical organization.
- Refined the intended organization around frequent conversations with Gu, Head, and persistent project PMs, with focused specialist sessions when useful.
- Distinguished using Codex-account models inside Pi from launching Codex CLI as a separately configured task-agent harness.
- Discussed short display names, project color grouping, explicit activity state, a details view, leadership fallback under hosted usage limits, and future bidirectional priority messaging through Gu.
- The supplied screenshot confirms the intended Herdr presentation at that time: project Spaces and grouped agents in the sidebar, with a two-column tab containing a terminal on the left and Pi on the right. It shows Pi 0.85.1, the Herdr state extension, and the then-current local `ollama/qwen3:4b-instruct` default. The model was replaced by Qwen3.5 9B on October 7; the screenshot remains historical evidence rather than the current runtime roster. No Pi update was authorized or performed.

### Decisions

- The personal assistant is named Gu, after 顾. DAO refers to the operating model or way work is done, not to the assistant.
- The portfolio manager is Head. The persistent project-specific liaison is Project Manager (PM), not Project Lead.
- Planner owns requirements, plans, acceptance criteria, checklists, session and decision records, and other project documentation. Dev Lead owns implementation approach, developer direction, and technical review.
- Documentation maintenance should normally become a bounded Planner task so it can run in parallel and other roles remain within scope. The PM or Head reconciles the result.
- The intended common conversation surfaces are Gu, Head, and PMs. Direct Designer, Dev Lead, or other specialist sessions remain available for focused discussion.
- Specialist agents use short display names such as `dev-12`; durable internal identity still includes project, task, role, and incarnation. Project-derived color grouping is preferred when supported, but color is not the only identity or state signal.
- Agent activity must be explicit through concise states such as working, thinking, delegating, waiting, reviewing, testing, needs input, done, and idle. A `/details`-style view should expose bounded operational detail.
- Head and PM require a continuity fallback when hosted usage is exhausted, but fallback is explicit rather than silent and does not silently weaken a high-impact review or approval gate.
- A Pi PM may eventually delegate to Codex CLI through an approved orchestration bridge that starts and observes the Codex agent and collects its handoff. Selecting a Codex model inside Pi alone does not provide Codex CLI tools.
- Gu should eventually relay messages bidirectionally between Discord, Head, and named PMs. Leadership-originated priority notifications are retained as a future requirement, not current implementation scope.
- The Discord bot should use the Gu identity. Renaming a dedicated n8n subdomain to Gu is directionally consistent, while n8n remains an implementation layer rather than the DAO orchestrator. Live renaming requires a separate migration task.
- The Gu/Discord implementation may live in a separate repository. The DAO repository continues to own portable operating definitions.
